# Agent 订餐行为规则

本文档是 `cafeteria-takeout` Skill 的 Agent 行为细则，补充 SKILL.md 中的流程骨架。

## 审查目标

- 确认 Agent 在非预订窗口时给出准确提示，不误导用户
- 确认菜品 state 字段的处理逻辑完整（区分 state=1 和 state=3）
- 确认下单失败时有结构化的降级处理，不直接抛出错误
- 确认对话规范中没有暴露技术细节给用户

## 认证说明

本 Skill 的脚本通过 uv 内联依赖引入 `ks_aimate`，并由 `SmartSSOSession` 自动处理 SSO 认证；业务侧不手动管理 Cookie、Session 或 Token。

## 时间窗口判断

**时间窗口检查是进入订餐流程的第一步。**
在向用户确认园区、区域、日期、餐型之前，必须先判断当前时间是否在预订窗口内。

| 当前时间 | 是否在窗口 | 可预订范围 | 提示语 |
|---------|-----------|-----------|--------|
| 00:00 - 10:00 | ✅ 晚间（跨天） | 当天午/晚餐 + 明天及以后 | 正常处理 |
| 10:00 - 12:00 | ❌ 窗口外 | — | 「现在是 HH:MM，可以在今天 12:00 后（午间窗口）来预订」 |
| 12:00 - 13:30 | ✅ 午间窗口 | 当天晚餐 + 明天及以后 | 正常处理 |
| 13:30 - 18:00 | ❌ 窗口外 | — | 「现在是 HH:MM，午间预订已结束，可以在今天 18:00 后（晚间窗口）来预订」 |
| 18:00 - 23:59 | ✅ 晚间窗口 | 明天及以后 | 正常处理 |

**不在窗口时：直接告知并结束当前订餐流程，不继续后续步骤，也不要再追问地址、日期、餐型或菜品。**

> **🚨 窗口外话术约束（必须严格遵守）**：
> 1. **提示必须与当前时间段匹配**：10:00-12:00 只能提示“12:00后可订”；13:30-18:00 只能提示“18:00后可订”。绝不能把这两个提示混在一起发给用户。
> 2. **只给下一个仍然有效的时间点**：如果现在已经是 14:22，说明“今天 12:00 后”这个时间点已经失效，不得再把它作为可选项发给用户，只能告知“今天 18:00 后可订”。

**在窗口内时，还需验证用户想订的日期是否合法：**

| 当前窗口 | 用户想订的日期 | 处理 |
|---------|-------------|------|
| 午间（12:00-13:30） | 当天午餐 | ❌ 已过预订时间，询问改为今天晚餐或明天 |
| 午间（12:00-13:30） | 当天晚餐 / 明天及以后 | ✅ 正常处理 |
| 晚间（18:00-23:59） | 当天任何餐 | ✅ 先调 `list` 接口查询当天菜品；接口返回为空或无可预订菜品再提示「今天这个餐段已经没有可订外卖了，是否改为明天？」 |
| 晚间（18:00-23:59） | 明天及以后 | ✅ 正常处理 |
| 跨天（00:00-10:00） | 当天午/晚餐 或明天及以后 | ✅ 正常处理 |
| 任何窗口 | 超出已发布菜单范围 | ✅ 先调 `list` 接口查询；接口返回为空再提示「该日期暂无可预订菜品，菜单可能尚未发布，周五 18:00 后可查看下周菜单」 |
| 周五 18:00 后至周日 | 查询下周某餐型 | ✅ 先调 `list` 接口查询；若该日期该餐型返回为空，不要先归因于“未发布”，应优先按“该餐型暂无外卖菜品”处理，尤其是早餐场景 |

## 地点确认规则

在进入菜单查询前，地点必须尽量确认到 **园区 + 区域** 两个层级。

| 场景 | 正确做法 |
|------|---------|
| 默认位置已包含园区 + 区域 | 一次性确认完整地点，如「这次还是在 北京·元中心 · T3 取餐吗？」 |
| 用户只说了园区，未说区域，且该园区有多个区域 | 同一轮直接列出全部区域供用户选择，不要先继续菜单流程 |
| 用户只说了园区，且该园区只有一个区域 | 可直接使用该区域，但最好在确认单中带出完整地点 |
| 用户园区、区域都没说清 | 先查默认位置；若仍不明确，再向用户一次性补齐地点信息 |

**目标是减少来回追问**：不要先问园区，下一轮再想起要问区域；也不要只确认区域而不说园区。

## 菜品查询为空时的处理

当 `list` 查询结果为空，或过滤到指定餐型后没有任何菜品可展示时，必须按场景判断，不要统一回答“菜单未发布”。

| 场景 | 处理方式 |
|------|---------|
| 周五 18:00 后至周日，查询下周早餐且结果为空 | 优先提示「该日期早餐暂无可订外卖」，引导用户改查午餐或晚餐；不要先归因为菜单未发布 |
| 已到下周菜单发布时间后，查询下周某餐型结果为空 | 优先按「该餐型暂无外卖菜品」处理 |
| 查询明显超出当前已发布范围的更远日期，且结果为空 | 可提示菜单可能尚未发布 |
| 查询当天或近期开餐时段结果为空 | 提示该时段暂无可订菜品，可能已售罄、已截止或当前不提供外卖 |

推荐话术示例：
- 「下周三的早餐目前没有可订外卖，你可以看看午餐或晚餐有没有菜品。」
- 「这个时段暂时没有可订外卖，可能是已经订完了，也可能这个餐段本身不提供外卖。」
- 「这个日期的菜单现在还没放出来，通常每周五 18:00 后可以看到下一周的菜品。」

## 菜品 state 字段处理

> 仅 Agent 内部参考，不对用户暴露字段名。

| state 值 | 含义 | 处理方式 |
|---------|------|---------|
| `"1"` | 已截止 | 提示已截止，推荐其他可订菜品 |
| `"3"` | 未开放（description 字段含开放时间，如「18:00 开始」） | 告知开放时间，询问是否等待或换其他菜品 |
| 其他 | 可预订 | 正常展示 |

## 下单失败处理

| 失败原因 | 处理方式 |
|---------|---------|
| 楼层余量不足 | 展示同菜品其他有余量楼层，让用户换层 |
| 菜品售罄 | 刷新菜单，推荐其他可订菜品 |
| 菜品已截止（state=1） | 展示其他未截止菜品 |
| 菜品未开放（state=3） | 告知开放时间，询问是否等待或换菜品 |
| 已有重复订单 | 调 `query` 展示已有订单，问是否取消重订 |
| 订餐已截止 | 告知截止，询问是否换日期 |
| 无订餐权限 | 告知无权限，建议联系行政 |
| 当前不在预订窗口 | 告知当前时间，说明下一个可预订时间 |

## 对话规范

- **所有答复必须基于接口返回或技能规则文档的客观事实，绝对不允许推测或编造（比如凭空推测菜单发布时间、编造取餐点等）**
- 只说人话，不暴露技术细节（不提 ID、Cookie、字段名、命令参数、`meal_type` 数值等）；若调用命令出错也不得将错误过程展示给用户，直接重试或以自然语言说明结果
- 出错时用自然语言描述原因，不粘贴报错原文
- 所有菜品、楼层、订单信息**必须通过接口实时获取**，不得猜测或伪造
- 取消订单前必须先 `query` 查询订单，不得要求用户自己提供订单号
- 不承诺「定时提醒」「自动下单」等功能，礼貌说明不支持
- **不得凭规则推断菜单是否已发布**：无论当前是什么时间，只要用户询问某日期的菜品，都应先调 `list` 接口查询；若接口返回为空再告知用户菜单暂无内容，不得事先断定「菜单还未发布」
- **用户未提供明确地址信息时，优先查默认取餐位置**：只有当默认位置也拿不到，或仍不足以确定具体区域时，才继续询问用户
- **查询到默认位置时，应先确认再追问**：不要在未查默认位置的情况下直接问「你在哪个园区订餐？」
- **地点确认应尽量一次完成**：只要进入地址确认环节，就应尽量在同一轮确认到“园区 + 区域”，避免把园区和区域拆成多轮零散追问
- **用户已明确说明园区时，不得再拿历史位置反问**：历史默认位置仅在用户未提及任何园区时才使用
- **园区下有多个区域时，必须列出全部区域供用户选择**，不得自动默认其中一个（如万家灯火大厦分东侧/西侧，两侧取餐点不同，必须让用户明确选择）

### 地点确认话术模板

- **默认位置完整时**：
  - 「检测到你上次在 北京·元中心 · T3 取餐，这次还是这里吗？」
- **只明确了园区，但该园区有多个区域时**：
  - 「北京·万家灯火大厦有东侧、西侧两个取餐区域，你这次选哪一个？」
- **园区和区域都不明确时**：
  - 「请告诉我你这次订餐的园区和区域；如果你不确定，我也可以先按你上次的取餐位置帮你确认。」
- **默认位置不存在时**：
  - 「我这边还没有查到你之前的取餐位置。请告诉我你这次订餐的园区和区域。」

要求：
1. 话术里尽量同时带出园区和区域，不要只说其中一个
2. 有多区域选项时，必须直接列选项，不要模糊追问
3. 地点未确认完整前，不继续进入菜单选择

## 常见违规与推荐修复

### 窗口外话术约束冲突（混用提示与时效错误）

- **违反规范**：在 13:30-18:00 窗口外时，使用了 10:00-12:00 的提示模板（如“可在 12:00 后来预订”），且给出了已经过期的时间点。
- **推荐修复**：根据当前时间严格匹配对应的窗口外话术。绝不能把多个提示混在一起，且只能给“下一个仍然有效的时间点”。如 14:22 只能说“今天 18:00 后可订”。
- **自动修复**：不支持。

### 对 state=3 的菜品提示「已截止」

- 违反规范：state=3 表示「尚未开放」，与 state=1「已截止」含义相反，不能混用。
- 推荐修复：state=3 时读取 description 字段中的开放时间并告知用户，如「该菜品 18:00 开始预订」。
- 自动修复：不支持。

### 取消订单时要求用户手动输入订单号

- 违反规范：Agent 不得要求用户自己提供订单号。
- 推荐修复：先调 `query` 获取订单列表，展示菜品名/日期让用户选择，再用结果中的 orderId 调 `cancel`。
- 自动修复：不支持。

### 下单失败时直接返回错误，无降级引导

- 违反规范：下单失败时应根据原因给出具体引导（换楼层、换菜品、查已有订单等）。
- 推荐修复：捕获失败原因，按「下单失败处理」表格执行对应的降级策略。
- 自动修复：不支持。

### 用户已说明园区却仍用历史位置反问

- 违反规范：用户已在对话中明确提到园区（如「在万家灯火」「元中心的外卖」），Agent 不应再拿历史默认位置确认，应直接使用用户说的园区。
- 推荐修复：解析用户意图时，如果用户未明确说明园区或区域，应先调用 `default-location` 获取默认取餐位置；仅在默认位置不存在或无法唯一确定时，再追问用户。
- 自动修复：不支持。

### 多区域园区未让用户选择区域直接默认

- 违反规范：部分园区（如万家灯火大厦）下有多个区域（东侧/西侧），每个区域的取餐点不同，不能自动默认。
- 推荐修复：调 `default-location` 后检查园区下的 `areaNameList`，若有多个区域，必须列出全部选项让用户明确选择其中一个，再继续后续步骤。
- 自动修复：不支持。
