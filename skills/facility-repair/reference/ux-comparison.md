# 用户体验优化对比

## 问题：技术参数暴露给用户

### ❌ 错误示例（暴露技术细节）

```
用户：帮我报修，元中心 T1-2层 智能卫生间不准

AI：
好的，正在帮你提交工单。

从查询结果中匹配到：
- 园区：北京·元中心 (parkId=58)
- 楼栋：1号楼 (buildId=75)
- 楼层：2层 (floorId=327)
- 服务类型：智能卫生间 (typeId=153)

正在提交...
```

**问题**：
1. ❌ parkId、buildId、floorId、typeId 这些是内部技术参数
2. ❌ 用户不需要知道这些 ID
3. ❌ 暴露了"查询结果匹配"这个内部过程
4. ❌ 显得笨拙、不专业

---

### ✅ 正确示例（用户友好）

```
用户：帮我报修，元中心 T1-2层 智能卫生间不准

AI：
好的，帮你提交工单：
- 位置：元中心 1号楼 2层
- 问题：智能卫生间显示不准
- 类型：智能化系统

马上为你提交 🔧

[稍后]

✅ 报修工单已提交成功！
- 工单号：178152
- 位置：元中心 1号楼 2层
- 问题：智能卫生间显示不准

行政同学会尽快联系你处理 🔧
```

**优点**：
1. ✅ 使用用户语言（元中心 1号楼 2层）
2. ✅ 没有技术参数（parkId、buildId 等）
3. ✅ 不暴露内部处理过程
4. ✅ 简洁、友好、专业

---

## 核心原则

### 1. 禁止暴露的技术参数

| 技术参数 | 用户语言 |
|---------|---------|
| parkId=58 | 元中心 |
| buildId=75 | 1号楼 / T1 |
| buildId=76 | 2号楼 / T2 |
| floorId=327 | 2层 |
| typeId=101 | 暖通 / 空调温度 |
| typeId=153 | 智能化系统 / 智能卫生间 |

### 2. 禁止暴露的内部过程

| 内部过程 | 说明 |
|---------|------|
| "调用 get_enums" | 用户不需要知道 |
| "从查询结果中匹配" | 用户不需要知道 |
| "运行脚本" | 用户不需要知道 |
| "正在查询枚举" | 用户不需要知道 |
| "匹配到 floorId" | 用户不需要知道 |

### 3. 用户只需要知道

| 阶段 | 用户需要的信息 |
|------|--------------|
| 提交前确认 | 位置、问题、类型（用户语言） |
| 提交中 | "正在提交..." |
| 提交成功 | 工单号、位置、问题 |
| 提交失败 | 简洁的错误提示 |

## 关键规则

### 对内（AI 内部处理）
1. 动态调用 `get_enums` 获取枚举
2. 从返回结果中匹配 parkId、buildId、floorId、typeId
3. 调用 `submit` 提交工单

### 对外（用户可见）
1. 使用用户语言（元中心、T1、T2、C5）
2. 不显示技术参数（parkId、buildId 等）
3. 不暴露内部过程（查询、匹配、运行脚本）
4. 简洁、友好、专业

---

## 总结

**技术实现 ≠ 用户体验**

- AI 内部可以用 parkId=58、buildId=75、floorId=327
- 但用户只需要看到"元中心 1号楼 2层"

**就像点外卖**：
- 用户说："给我来份宫保鸡丁"
- 商家内部：菜品ID=1001、规格=标准、辣度=中辣
- 用户看到的：✅ 您的宫保鸡丁（标准份，中辣）已下单

**不应该说**：
- ❌ "您点的菜品ID=1001已匹配到库存，规格ID=2，辣度ID=3..."
